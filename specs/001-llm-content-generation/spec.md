- Q: Should LLM output existing custom patch format ({"add": {...}}, {"remove": {...}}, {"replace": {...}}) or JSON Patch RFC 6902? → A: A - LLM outputs existing custom format directly.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Extract Atoms from Source Content (Priority: P1)

A content creator provides grounding material (text files, VTT subtitles) and wants the system to extract meaningful atoms that capture relationships, processes, comparisons, and key statements rather than just flat bullet points.

**Why this priority**: This is the foundational capability - without atom extraction, there's no structured input for layout generation. It's the first step in the content pipeline.

**Independent Test**: Can be fully tested by providing a text file and verifying that the system extracts atoms with proper relationships and source links, deliverable as structured data independent of layout generation.

**Acceptance Scenarios**:

1. **Given** a plain text file with process steps, **When** atom extraction is triggered, **Then** atoms are extracted as a list structure with relationships between steps preserved
2. **Given** a VTT subtitle file with dialogue and timestamps, **When** atom extraction runs, **Then** atoms contain relevant statements linked to their source timestamps
3. **Given** content with comparisons between concepts, **When** atoms are extracted, **Then** comparison atoms are structured as tables with relationships between compared items
4. **Given** extracted atoms, **When** inspecting atom metadata, **Then** each atom has a link back to its source file and location

---

### User Story 2 - Generate Layout Content with State Management (Priority: P2)

A user wants to generate slide layouts with actual content, where the system manages generation state by transitioning slides to DRAFT during updates and ACTIVE when generation completes.

**Why this priority**: This delivers the end-to-end value proposition - turning atoms into presentation-ready layouts. Depends on P1 atom extraction being functional.

**Independent Test**: Can be tested by providing extracted atoms and verifying that slides progress through DRAFT state during generation before finalizing to ACTIVE with complete content matching layout schema requirements.

**Acceptance Scenarios**:

1. **Given** extracted atoms, **When** layout generation begins, **Then** a patch is generated updating slide states to DRAFT (updating process)
2. **Given** slides in DRAFT state, **When** content generation completes, **Then** slides contain layout config with text matching supported layout attributes
3. **Given** completed content generation, **When** patch is applied, **Then** slide states update to ACTIVE (generation complete)
4. **Given** layout schema with supported widget types, **When** LLM generates content, **Then** output strictly adheres to layout config schema without unsupported attributes

---

### User Story 3 - Apply Patches to Patchable Collections (Priority: P1)

The system needs to manage incremental changes to both Atom and Content collections through a patch mechanism, allowing the application code to maintain full context throughout the generation process.

**Why this priority**: Equal priority with P1 because patch management is the core architectural pattern enabling both atom and content workflows to function properly.

**Independent Test**: Can be tested by creating a patchable collection, generating patches for modifications, and verifying that patches apply correctly while maintaining collection state and history.

**Acceptance Scenarios**:

1. **Given** an Atom collection, **When** LLM outputs an atom extraction patch, **Then** the patch applies to the collection without replacing entire context
2. **Given** a Content collection with slides, **When** a state transition patch is applied, **Then** only specified slides change state while others remain unchanged
3. **Given** multiple patches generated in sequence, **When** patches are applied in order, **Then** collection state evolves correctly through all intermediate states
4. **Given** a PatchableCollection implementation, **When** Atom and Layout classes inherit from it, **Then** both types support patch operations with consistent behavior

---

### User Story 4 - Two-Flow Separation: Atoms vs Layouts (Priority: P3)

The system separates atom management from layout generation into distinct flows, where user instructions flow through atom extraction first, then full atom context feeds into layout generation.

**Why this priority**: This architectural separation ensures clean concerns and testability, but the feature can function with a simpler integrated approach initially.

**Independent Test**: Can be tested by observing that atom extraction completes independently and produces output usable by layout generation flow without coupling between the two processes.

**Acceptance Scenarios**:

1. **Given** user instructions with source files, **When** processing begins, **Then** atom extraction flow executes first and completes before layout generation
2. **Given** completed atom extraction, **When** layout generation flow begins, **Then** full atom context is available as input
3. **Given** atom extraction failure, **When** layout generation is attempted, **Then** layout generation does not proceed without valid atoms
4. **Given** separated flows, **When** modifying atom extraction logic, **Then** layout generation logic remains unaffected

---

### Edge Cases

- What happens when source content is empty or contains no extractable atoms?
- How does the system handle atom extraction when relationships between content are ambiguous or contradictory?
- What occurs if LLM generates layout content with unsupported attributes not in the schema?
- How does patch application behave when a patch references non-existent collection items?
- What happens when slide state transitions occur out of expected sequence (e.g., active → draft instead of draft → active)?
- How does the system handle very large source files that exceed LLM context windows?
- What occurs when atom extraction produces duplicate or overlapping atoms from the same source location?

## Requirements *(mandatory)*

### Functional Requirements

#### Source Management
- **FR-001**: System MUST accept plain text files (.txt) as source content for atom extraction
- **FR-002**: System MUST accept VTT subtitle files (.vtt) as source content for atom extraction
- **FR-003**: System MUST associate each source with a name or link identifier
- **FR-004**: System MUST preserve source file metadata for traceability

#### Atom Extraction
- **FR-005**: System MUST extract atoms from source content using LLM processing
- **FR-006**: Each atom MUST maintain a link to its source file and location
- **FR-007**: Atoms MUST capture relationships between content elements, not just flat lists
- **FR-008**: System MUST support multiple atom types as separate subclasses: StatementAtom (pure text), ProcessAtom (list with steps), ComparisonAtom (table structure), all inheriting from base Atom class
- **FR-009**: Atom extraction output MUST be structured patches for PatchableCollection
- **FR-010**: System MUST store atom extraction logic in `src/generation/atom` directory

#### Content/Layout Generation
- **FR-011**: System MUST generate layout configurations conforming to the existing layout schema
- **FR-012**: LLM-generated content MUST strictly use supported layout config attributes only
- **FR-013**: Content generation output MUST be structured patches for PatchableCollection
- **FR-014**: System MUST store content generation logic in `src/generation/content` directory
- **FR-015**: Content generation MUST use full atom context as input

#### State Management
- **FR-016**: Each slide and atom MUST use PatchableContextState enum (DRAFT/ACTIVE/ARCHIVED/DELETED)
- **FR-017**: Content generation MUST follow two-step state transition: first patch sets slides to DRAFT (updating process), second patch generates content and sets to ACTIVE (generation complete)
- **FR-018**: System MUST generate state transition patches before content patches
- **FR-019**: Normal generation flow transitions entities from DRAFT (during update) → ACTIVE (completed)

#### Patchable Collections
- **FR-020**: Individual Atom entities MUST inherit from PatchableContextBase (like Slide), and AtomCollection MUST inherit from PatchableCollection (like Slides) for managing atom instances
- **FR-021**: PatchableCollection MUST support applying incremental patches without full replacement
- **FR-022**: Patches MUST preserve full context state throughout generation process
- **FR-023**: System MUST manage collection state through patch application
- **FR-024**: LLM MUST output patches using existing custom format: AddOperation ({"add": {...}}), RemoveOperation ({"remove": {"id": "..."}}), ReplaceOperation ({"replace": {...}})

#### Workflow Separation
- **FR-025**: System MUST implement separate flows: atom management flow and layout generation flow
- **FR-026**: User instructions MUST be passed to atom extraction flow first
- **FR-027**: Full atom context MUST be passed to layout generation flow after atom extraction completes
- **FR-028**: Atom extraction flow MUST complete before layout generation flow begins
- **FR-029**: Layout generation flow MUST NOT modify atom collection state

#### LLM Response Caching
- **FR-030**: System MUST cache LLM responses using hash-based filesystem caching
- **FR-031**: Cache keys MUST be SHA256 hashes of (prompt + input content)
- **FR-032**: Atom extraction cache MUST be stored in `.cache/atoms/` directory
- **FR-033**: Layout generation cache MUST be stored in `.cache/layouts/` directory
- **FR-034**: Cache hits MUST return responses without making LLM API calls

### Key Entities

- **Source**: Grounding content input (text file, VTT subtitle file) with name/link identifier and file metadata for traceability
- **Atom** (base class): Abstract base class inheriting from PatchableContextBase with source reference, relationship metadata; includes id, rank, and state fields from base class
- **StatementAtom**: Concrete atom subclass for pure text statements with text content field
- **ProcessAtom**: Concrete atom subclass for process steps with list/sequence structure preserving step relationships
- **ComparisonAtom**: Concrete atom subclass for comparisons with table structure showing compared items and their attributes
- **AtomCollection**: Collection manager (inheriting from PatchableCollection) for managing Atom instances with rank-based ordering and patch operations
- **Content/Layout**: Layout configuration with text content, widget definitions, and state field (initial/draft/active); inherits from PatchableCollection
- **Patch**: Incremental modification instruction containing operation type, target collection, affected items, and state changes
- **PatchableCollection**: Base class providing patch application, state management, and context preservation capabilities
- **AtomFlow**: Processing pipeline managing atom extraction from sources using LLM
- **LayoutFlow**: Processing pipeline managing layout generation from atoms using LLM

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Atom extraction processes source files and produces structured atoms with source links in under 10 seconds for typical 1000-word documents
- **SC-002**: Generated layout content adheres to layout schema with 100% compliance (no unsupported attributes)
- **SC-003**: Slide state transitions follow the correct sequence (DRAFT during update → ACTIVE when complete) in 100% of generation runs
- **SC-004**: Patch application maintains collection context consistency across 100+ sequential patch operations
- **SC-005**: Atom extraction preserves relationships between content elements in at least 90% of process descriptions and comparison scenarios
- **SC-006**: Content generation completes two-step state transition (draft creation + content generation) within 30 seconds for typical 10-slide presentations
- **SC-007**: System successfully separates atom and layout flows such that atom extraction can run independently and complete without layout generation dependencies
- **SC-008**: Cache hit rate exceeds 80% during iterative development/testing scenarios with repeated source content

## Assumptions

- LLM service is available and accessible for both atom extraction and content generation
- Layout schema is well-defined and documented for LLM instruction
- Initial implementation focuses on text-based sources; image/video sources deferred to future iterations
- Patch serialization format will use JSON for LLM compatibility
- State management uses simple string states without complex state machines initially
- Atom relationship modeling uses nested structures within atom format types (lists, tables) rather than explicit graph representations
- PatchableCollection implementation will use Python base class with standard inheritance
- Error handling for LLM failures will use retry mechanisms with exponential backoff
- Context window limitations will be addressed by chunking large sources in future iterations

## Dependencies

- Existing layout engine and rendering system (completed in previous round)
- Layout configuration schema documentation
- LLM service API integration
- File I/O capabilities for reading .txt and .vtt files

## Out of Scope

- Planning/navigation stage to route between atom and layout flows (explicitly deferred for initial implementation)
- Support for non-text source formats (images, videos, PDFs)
- Manual editing interface for atoms or layouts
- Version control or history tracking beyond basic patch application
- Multi-user collaboration or concurrent editing
- Real-time generation or streaming updates
- Atom conflict resolution when multiple sources produce overlapping atoms
- Performance optimization for very large corpora (>100MB source files)
