Traditional AI: Linear, role‑separated pipeline

  • Data engineers: collect and curate data
  • Researchers: select or design models
  • ML engineers: train and tune for accuracy
  • Developers: deploy, latency and throughput
  • Product: measure user impact, plan iterations
  1. 1. Collect and curate data (coverage, quality)
  2. 2. Select or design model structure
  3. 3. Train and tune to maximize accuracy
  4. 4. Deploy, optimize latency and throughput
  5. 5. Measure impact, iterate slowly with tweaks
  • Slow, months‑long iteration cycles
  • Expensive to build and operate
  • Frequent reinvention of infrastructure
  • Rebuilt evaluation and optimization each project
  • Strong contrast with fast LLM‑era workflows

Building Reliable LLM Systems

  • Start with a general prompt for ~90% of typical cases
  • Observe outputs to find edge cases and failure modes
  • Add explicit constraints and instructions to handle those cases
  • Repeat until remaining failures are at an acceptable level
  • LLM acts as high-level planner suggesting steps or actions
  • Executor (non-LLM code) runs steps and tracks authoritative state
  • Persist critical state outside the LLM as structured data
  • Executor validates steps, triggers retries or alternative plans
  • Feedback loop stops small errors from compounding into wrong outcomes
  • Prevent error accumulation with explicit planning–execution architectures
  • Prompts are not enough without verification and state control
  • Humans still lead at C++ intrinsics and memory/cache behavior
  • Engineers must scope problems correctly across system boundaries

Where humans still beat LLMs

  • Define problem scope before coding
  • Ask: what actually needs to be fast?
  • Question whether optimization is valid at all
  • Avoid micro-tuning a local function
  • Check if it runs 38 times/second
  • Prefer once per lifecycle over tiny tweaks
  • Focus on high-ROI technical work
  • Integrate telemetry and adaptive loops
  • Ship features that better meet customer needs
