How traditional AI pipelines were organized

Traditional AI: linear, role-siloed

1. Data collection

2–3. Models and training

4–5. Deployment and impact

Slow, linear pipeline with fixed ownership across data, models, training, deployment, product.

  • Collect and curate data
  • Ensure coverage and quality
  • Owned by data engineers
  • Select or design architecture
  • Train and tune for accuracy
  • Model scientists focus here
  • Deploy into production systems
  • Optimize latency, throughput
  • Measure user and product impact
  • Engineers and product own stages

Result: slow, expensive, infra-heavy; teams repeatedly rebuilt evaluation and optimization each project.

Shift to the LLM / large model era

Traditional AI era

LLM / large model era

  • Standalone models, siloed knowledge
  • Linear pipelines, built from scratch
  • Micro‑optimizing training pipelines
  • Clear data / model / infra roles
  • Large models as unified knowledge
  • Compose via prompts, tools, agents
  • Optimize prompts, workflows, evaluation
  • Blurred engineer–scientist boundaries

Large models provide a shared reasoning layer; you build on top, not from scratch.

Engineers emphasize stability; scientists push model boundaries and orchestration for new features.

As a developer, focus on orchestration, prompting, and product impact in this new stack.

Building reliable LLM features

Beyond “just call the API”

  • planner‑executor: LLM plans steps
  • Executor tools run steps, track state
  • Keep critical state in structured data
  • Validate each step; trigger replanning
  • Stop small errors from snowballing
  • Prompt tuning helps but limited
  • Cover ~90% cases with base prompt
  • Collect real failures, edge cases
  • Iteratively refine constraints, clarifications
  • Combine prompts with external verification

Use planner‑executor architecture plus disciplined prompt tuning to reach production reliability.

Using AI as a Power Tool

AI as a power tool: start from the task, not the tool

  • Start from a concrete need or task
  • Write a clear abstract or spec as source of truth
  • Use AI tools to translate spec into slides, docs, diagrams, code structure
  • Iterate on spec and outputs, then reuse workflow for future projects

Treat your human‑written spec as the single source of truth that AI repeatedly translates into multiple artifacts.

Pattern: task → spec → AI-generated artifacts → iterate and reuse
