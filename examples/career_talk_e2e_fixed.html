Planner–Executor Architecture Pattern to Learn

Plan with an LLM planner

Structure the steps

Execute with a guardian

Detect failure and replan

Use a planner component, often an LLM, to generate a high-level plan consisting of discrete steps for the task.

Represent each step in a structured, persistent form such as data rather than free text instructions.

Use an executor component, not necessarily an LLM, to carry out each step while maintaining accurate state and verifying feasibility.

If the executor detects that a step cannot be executed or leads to inconsistency, signal failure back to the planner, revise the plan, and repeat execution and verification with real-time feedback.

Practical Prompting & Tooling

Working with Prompts and LLM Tools (Without Losing Your Mind)

Slide 28 · Section · Pragmatic prompting for real projects

Iterative Prompt Tuning Strategy That Actually Works

Start with a 90% prompt

Observe outputs and edge cases

Add constraints for the last 10%

Repeat until bad cases are acceptable

Define a general prompt that captures the main task and works for the common path, roughly 90% of typical cases.

Run the system and watch where it fails; identify edge cases and failure modes from real data or examples.

Augment the prompt with explicit instructions to avoid or handle the identified edge cases and tricky scenarios.

Iterate on this loop until the remaining bad cases are reduced to a level that is acceptable for your product and users.

Slide 29 · Use prompts like you debug code: iterate on real failures

Reality Check: Limits of Prompt Tuning

Not a silver bullet

Prompt tuning cannot solve all hallucination or error problems; it is one tool in a bigger system design toolbox, not magic on its own.

Last 10% matters

Success includes resolving the last 10% of bad cases, not just making the first 90% work; this often needs architecture and evaluation, not only prompt tweaks.

Error accumulation is real

In large-model systems, small inaccuracies can compound into garbage outputs; this is why patterns like planner–executor and validation loops are important beyond prompt text alone.

Sustainable Learning in the AI Firehose

Stay Current Without Burning Out on Every New Model Drop

Slide 32 · Section · Staying up to date without chasing every tool

How to Keep Up with AI Like a Working Dev

Skim for Direction, Dive Only When Needed

  • Subscribe to an app or service that recommends new research papers in selected AI categories.
  • Choose three to four categories that align with your interests or work focus.
  • Skim recommended papers to understand main ideas and the direction of each category instead of reading everything deeply.
  • Deep dive into specific papers only when they are highly relevant to your current needs.
  • Do not feel pressure to try every new AI tool; use tools in a task-driven way when there is an actual need.
  • This approach keeps you aware of trends without burning out on constant novelty.
  • For your own learning, pick a few themes (e.g., LLM tooling, evaluation, agents) and track them over time.
  • Use real tasks at work or in side projects to justify deeper dives; avoid learning in a vacuum.
  • Let this rhythm guide your learning instead of chasing every announcement or benchmark result.

This is how the speaker keeps up with AI: skim broadly, dive when necessary, and use tools when there is a concrete task to solve instead of collecting tools for their own sake.

What Entry-Level Devs Can Do Now

  • Make every step solid, whether writing code, designing systems, or asking questions.
  • If you ask a question and eventually understand the answer, that Q&A pair becomes solid knowledge.
  • If you never understand the answer, you gain nothing; treat understanding as the goal, not just asking.
  • Strong fundamentals in coding and systems are still the base for all AI work.
  • Practice precise problem formulation as a first key area for high return on effort.
  • Use daily-life scenarios and side projects to imagine more useful products, not just what models can do today.
  • Reflect on scope: ask whether you are solving the right problem at the right level before jumping into code or prompts.
  • Run small prompt and LLM experiments on real tasks you care about instead of only toy problems.
  • Use the 90% prompt → observe → add constraints → repeat loop to see how behavior changes.
  • Treat LLMs as collaborators that turn your spec into artifacts, not as oracles that always know the answer.
  • Start simple evaluation habits: write down what "good" means for your feature and check it regularly.
  • Practice building tiny feedback loops, even if they are manual at first, so you think in terms of iteration.
  • Over time, move toward automatic checks and telemetry so you can iterate faster with confidence.
