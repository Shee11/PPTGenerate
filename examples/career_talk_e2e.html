Why Prompts Alone Are Not Enough

Prompt Tuning Limits

System‑Level Reliability

  • Prompt tuning is not a silver bullet.
  • It can reduce some hallucinations and errors.
  • It will not fix all reliability issues.
  • Error accumulation across multiple steps is a core challenge.
  • Small mistakes in each step can compound into garbage outputs.
  • You need architecture patterns, not just better prompts.
  • Treat prompts as one tool, not the whole toolbox.
  • Design flows that validate and correct as they go.

Slide 12 · Think beyond prompts to full architectures

Architecture Pattern: Planner–Executor for LLM Apps

Planner–Executor Pattern

  • Planner (often an LLM) does high‑level reasoning and creates a plan.
  • Steps are stored as structured, persistent data (not just context).
  • Executor component (LLM or deterministic) executes each step.
  • Executor maintains state and enforces constraints.
  • If a step fails, executor signals the planner.
  • Planner retries, adjusts the plan, or chooses a new approach.
  • Repeat planning + execution with feedback.
  • Prevents small errors from accumulating into large failures.
  • Use LLMs as planners, executors, and data validators together.
  • Design your side projects to practice this pattern.

Slide 13 · A practical pattern to build reliable workflows

Where Humans Still Outperform LLMs

LLM Limits Today

Human Strengths Today

LLM coding tools are weak at low‑level optimization (intrinsics, memory layout, cache behavior).

You can reason about hardware, performance trade‑offs, and real bottlenecks.

LLMs struggle to choose the correct problem scope.

You can decide whether to optimize a function or change the whole flow.

They may find locally optimal fixes that are globally wrong.

You can zoom out and redefine the problem when needed.

Example: heavily optimized a function called 38 times/second.

Real fix: change the system so it runs once per lifecycle instead.

Slide 14 · Lean into problem scoping and system thinking

Mastering Problem Scope

Problem Scope
  • Different scopes yield different correct answers.
  • A solution optimal at one scope may be wrong at a broader scope.
  • Defining scope is a key human advantage today.
How to Practice
  • When debugging, always ask: “What if I zoom out one level?”
  • When using LLMs, try multiple problem framings before coding.
  • Treat scope definition as a first‑class design step.

Slide 17 · Curiosity and flexibility beat fixed labels over time

Practicing Problem Definition

Problem Definition as a Core Skill

  • One of the highest‑ROI areas for developers.
  • Explicitly includes data feedback and open‑ended exploration.
  • High‑value skill in the LLM era: define problems well before you solve them.
  • Humans still outperform LLMs at defining the right scope.
  • Practical exercise: imagine how products could be more useful in your daily life.
  • Do not limit ideas to what current models can do today.
  • There is no step‑by‑step recipe.
  • Instead, build a habit of asking: “What would be truly useful here?”
  • For each idea, try framing the problem at system, feature, and interaction levels.
  • Use LLMs to explore options, but keep ownership of the framing.

Staying Current Without Burning Out

Track Directional Trends

Adopt Tools Task‑First

Use LLMs as Translators

Practical Routine

  • Subscribe to 3–4 AI categories and scan new papers.
  • Do not deeply dive into every paper; watch where each category is moving.
  • Do not try every new AI tool just because it exists.
  • Adopt tools when you have a real task they can help with.
  • Treat LLMs as translators between specs, slides, docs, diagrams, and code.
  • Aim for a single spec as the source of truth for multiple artifacts.
  • Weekly: scan papers and note 1–2 trend shifts.
  • Projects: start from a written spec, then use LLMs to generate slides and diagrams.
  • Iterate on the spec instead of manually editing every artifact.
